# AI Context Init Design

**Date:** 2026-05-25
**Status:** Approved

## Problem

Developers (and the AI coding tools assisting them) have no visibility into the project's architectural rules until violations surface at test time. The `ag-arch-rules` package encodes these rules as executable fitness functions, but the rules are opaque to AI coding assistants that generate code before the test suite runs. The result is that developers produce violations they could have avoided if the rules had been part of the AI's context upfront.

## Goals

- Add an `ag-arch-rules init` CLI command that generates AI tool context files in the consuming project.
- Support Cursor, Claude Code, and Gemini as output targets.
- Let developers select which rule sets apply to their project so generated context is targeted, not generic.
- Re-running the command overwrites existing generated files so context stays current as the package evolves.

## Non-Goals

- ESLint plugin or IDE linting integration (the layer-dependency rules operate at graph level and cannot be expressed as file-level AST rules without a full reimplementation).
- Postinstall auto-generation (opt-in via explicit command is preferred — generated files should be visible and intentional in git).
- Programmatic export of structured rule metadata (a separate concern; not needed for this feature).

## Invocation

Added as a `bin` entry in `package.json`:

```json
"bin": {
  "ag-arch-rules": "./dist/bin/init.js"
}
```

Run via:

```sh
npx ag-arch-rules init
# or
pnpm exec ag-arch-rules init
```

## Interaction Flow

Two sequential multi-select prompts:

**Step 1 — Which AI tools?**

```
Which AI tools should we generate context files for?
  ◉ Cursor
  ◉ Claude Code
  ○ Gemini
```

At least one must be selected.

**Step 2 — Which rule sets apply to this project?**

```
Which rule sets apply to this project?
  ◉ Frontend (React/TypeScript)
  ○ Backend Node (Express/TypeScript)
  ○ CDK (AWS CDK infrastructure)
```

Common rules are always included and not presented as an option — they apply to every project type.

**Step 3 — Generate and report**

Files are written (or overwritten) silently, then a summary is printed:

```
✓ .cursor/rules/ag-arch-rules-common.mdc
✓ .cursor/rules/ag-arch-rules-frontend.mdc
✓ CLAUDE.md  (section created or updated)
```

## Output Per Tool

### Cursor

One `.mdc` file for common rules plus one per selected rule set, written to `.cursor/rules/`.

File naming: `ag-arch-rules-common.mdc`, `ag-arch-rules-frontend.mdc`, `ag-arch-rules-backend-node.mdc`, `ag-arch-rules-cdk.mdc`.

Each file uses Cursor's MDC frontmatter. Common rules use `alwaysApply: true`. Preset-specific files use `globs` to auto-attach when relevant source files are open in context:

```
---
description: AG architectural rules — frontend layer constraints
globs: src/components/**,src/pages/**,src/hooks/**,src/apis/**
alwaysApply: false
---
```

Re-running overwrites all generated `.mdc` files unconditionally.

### Claude Code

A fenced section is appended to `CLAUDE.md` (created if absent):

```markdown
<!-- ag-arch-rules: begin -->
## Architectural Rules

...rule content...

<!-- ag-arch-rules: end -->
```

On re-run, the section between the sentinel comments is replaced. Content outside the sentinels is preserved.

### Gemini

`GEMINI.md` is created or overwritten entirely. Because `GEMINI.md` is typically owned by tooling rather than developers, a full overwrite is safe and simpler than sentinel-based replacement.

## Content Source

Rule descriptions are authored as static template strings in the package source (`src/bin/templates/`), one file per rule set. Content is written for an AI audience — concise, actionable, focused on what the rule prohibits and why — rather than being a verbatim copy of `docs/RULES.md` (which is a developer reference). Templates are the source of truth; `RULES.md` remains the human reference.

All generated files include a header:

```
Generated by ag-arch-rules v{version} — re-run `ag-arch-rules init` to update.
```

## Dependencies

`@clack/prompts` added as a production dependency (it runs at init time in the consuming project, not at build time). It is small, has no sub-dependencies, and provides good interactive CLI UX.

## Files Added / Modified

| File | Change |
|---|---|
| `package.json` | Add `bin` entry; add `@clack/prompts` dependency; add `src/bin/` to build |
| `src/bin/init.ts` | Entry point — orchestrates prompts and delegates to generators |
| `src/bin/generators/cursor.ts` | Writes `.cursor/rules/*.mdc` files |
| `src/bin/generators/claude.ts` | Writes/updates `CLAUDE.md` section |
| `src/bin/generators/gemini.ts` | Writes `GEMINI.md` |
| `src/bin/templates/common.ts` | Rule content for common rules |
| `src/bin/templates/frontend.ts` | Rule content for frontend rules |
| `src/bin/templates/backend-node.ts` | Rule content for backend Node rules |
| `src/bin/templates/cdk.ts` | Rule content for CDK rules |
| `tsup.config.ts` (or build script) | Include `src/bin/init.ts` as an additional entry point |
